## 1. The unit selector says which code the checks come from

The selector is named after design codes — CIRSOC, Eurocode, NBR 8800,
CSA S16, AISC 360 — and that is honest about the UNITS: each entry really
is the convention that code tabulates in. It was silent about strength.
Every tab's resistance factors, nominal strengths and weld rules come from
`cirsoc_301.py` whichever entry is picked, so choosing "AISC 360 (US
customary)" changed kN to kip and nothing else. A student could reasonably
have read the selector as switching codes.

Two ways to fix that. Renaming the entries to "AISC units (kip, ft, in)"
makes it truthful by saying less; saying which code governs makes it
truthful by saying more. For a tool whose users are learning how codes
work, *"these are CIRSOC factors shown in AISC units"* is itself worth
knowing, so the selector keeps its names and the bar gains a line:

> **Strength checks use CIRSOC 301-2018 factors — only the units follow
> AISC 360 (US customary).**

It appears only when the two differ, so picking CIRSOC leaves the bar
quiet. `units.CHECKS_CODE` is the one place the name lives and
`CHECKS_NATIVE_TO` the one place the exception list lives, so implementing
a second code removes the caveat for the conventions it covers without
touching the UI.

## 2. Tier 3 — readability

**Material and section presets.** "Steel" is a thing an architecture
student knows; `E = 200` is not. The material list fills E (steel,
stainless, aluminium, reinforced concrete, glulam GL24h, softwood C24) and
a short IPE list fills A and I. The boxes stay editable underneath, and
the preset is written in whatever convention is selected, so picking AISC
and then "Steel" types ≈29 000 ksi rather than 200.

**Support types are symbols.** A `ttk.Combobox` of four words was the
wrong control for four things with universally recognised drawings — and
the tab already draws all four. The picker is now those drawings, and the
stored value is still `pin` / `rollerX` / `rollerY` / `fixed`, so no saved
model or workbook changes meaning.

**Text size, app-wide.** This project writes its fonts as literals, and a
good deal of the explanatory text is 7 or 8 point grey: legible on the
machine it was written on, not on a projector. A `Text: 100/125/150/175%`
control sits beside the units selector. `common.TextScale` walks the built
window rather than the hundreds of font literals, covering both named
fonts (which is the only way to reach ttk widgets) and per-widget ones,
and it remembers each widget's ORIGINAL size so repeated changes do not
compound and 100% returns exactly where it started. Panels that have not
had their sash dragged widen to suit.

**Joints are lettered.** On the canvas a joint number and a member number
sit a few pixels apart and look identical — "2" next to "2", with nothing
saying which is which. Joints are now A, B, C… and members stay numbered,
the convention every structures textbook uses. **Scope, deliberately:**
the drawing only. Every sentence still says "Node 2 · joint C" so the
drawing and the tables can be matched up, and the workbook, the PDF and
`truss_stability`'s wording keep plain indices — a letter in a saved file
would be a new identity to keep in step with the model, and the ambiguity
being fixed is a drawing problem.

## 3. Where does this load go?

The largest unbuilt teaching feature, and the one reading the numbers do
not hand you. View ▸ **Trace where one load goes** takes the selected
loaded joint (or the biggest load in the model) and animates chevrons
along every member carrying part of it, ringing each support with the
share that lands there:

> The load at B lands on: A 75%, E 25%. Its hardest-working member is rod
> 0 at −36.02 kN.

**It is computed by superposition, and that matters.** The structure is
linear elastic, so the answer for all the loads together is exactly the
sum of the answers for each one alone. `apps/truss/truss_loadpath.py`
re-solves the model with the chosen load and nothing else; the member
forces that come back ARE its path, and the reactions are exactly where it
lands. Nothing is estimated.

**The version thrown away.** The first implementation walked the joints,
splitting the load at each one between the members resisting it. It looked
entirely reasonable and it was wrong: on this project's own Warren truss
it reported a quarter-point load going **100% to the near support**, where
statics says **75/25**. A load path drawn from a plausible rule that
disagrees with the reactions teaches something false and the student has
no way to catch it. `test_a_quarter_point_load_splits_75_25` and
`test_superposition_reconstructs_the_real_solve` exist because of that;
the second checks the single-load solves add back up to the full one, and
they agree to 1e-9.

## 4. The pre-existing test failure, fixed at its cause

`t 01` reported one failure it did not cause:
`test_analysis_still_shows_diagrams_after_a_report_window_opened` passed
alone and failed in a full run, on pristine v32 too, with
`TclError: image "pyimage1" doesn't exist`.

Reproduced rather than guessed at. A Tk image belongs to ONE interpreter,
and `common.render_math` created it with no master, so Pillow bound it to
`tkinter._default_root` — the FIRST root the process ever made, which is
not necessarily the window being built. Two live roots and the equation
images are created in one interpreter and shown in another. `render_math`
now takes a `master` and the Rod Calculations report passes its own
window.

**It is an app bug, not a test bug.** One process with two Tk roots is
rare in normal use and routine in a test suite, which is only where it
surfaced.
